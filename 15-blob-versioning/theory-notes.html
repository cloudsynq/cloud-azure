Azure Blob Versioning & Blob Snapshots

Cloud Computing · Module 4: Azure Storage

1. What is Azure Blob Versioning?

Blob Versioning is a feature of Azure Blob Storage that automatically saves a new version every time a blob is modified or deleted. You can go back and restore any previous version at any time.

When enabled, every blob has a current version and one or more previous versions. Each version is identified by a unique Version ID (a timestamp-based string).

Analogy
Blob Versioning is like Word document "Track Changes" + Version History. Every time you save (overwrite) a file, the old version is automatically preserved. If you make a mistake, you can go back and restore the previous copy.

How it works

Blob: report.pdf ───────────────────────────────────────── Current Version → Version ID: 2026-10-12T10:30:00Z (latest file) Previous Version → Version ID: 2026-10-10T09:00:00Z (2 days ago) Previous Version → Version ID: 2026-10-08T14:20:00Z (4 days ago) ───────────────────────────────────────── Each version is stored separately and billed per GB. You can restore any version → it becomes the new current version.

When is a new version created?

  • When you overwrite a blob (upload same filename again)
  • When you modify blob metadata or properties
  • When a blob is deleted (a version is preserved before deletion)
Key Point
Even after deletion, previous versions are still accessible. A delete does NOT permanently remove all versions — it just removes the current version. You can restore by copying a previous version back as the current.

2. What is a Blob Snapshot?

A Blob Snapshot is a manually triggered, read-only copy of a blob at a specific point in time. Unlike versioning (which is automatic), snapshots are taken on demand by the user.

Analogy
Snapshot = taking a photograph. You decide when to click. Versioning = CCTV camera recording automatically. Both preserve history, but one is manual and one is automatic.

Snapshot properties

  • Identified by a DateTime timestamp appended to the blob URL
  • Read-only — you cannot modify a snapshot directly
  • Billed for the difference from base blob (incremental storage)
  • Can be promoted to become the current blob (restore)
  • Snapshot URL format: https://account.blob.core.windows.net/container/file.txt?snapshot=2026-10-12T10:30:00Z

Microsoft Recommendation
Microsoft recommends using Blob Versioning over Blob Snapshots for most use cases — it is automatic and easier to manage. Use Snapshots only when you specifically need a manual checkpoint.

4. Soft Delete (Bonus Topic)

Soft Delete protects individual blobs from accidental deletion. When enabled, a deleted blob is not immediately removed — it is marked as "soft deleted" and kept for a retention period (1–365 days) before permanent deletion.

  • Enable at Storage Account level → Data management → Data protection
  • Set retention period (e.g., 7 days)
  • Deleted blobs appear with a deleted flag — hidden by default in portal
  • Can be restored within retention period using Undelete operation
  • After retention period → permanently deleted
Best Practice
Enable Soft Delete + Blob Versioning together for maximum protection: Versioning handles overwrites, Soft Delete handles accidental deletes.

5. Important Exam Points

  • Blob Versioning = automatic, triggered on every overwrite/delete.
  • Blob Snapshot = manual, taken by user on demand.
  • Both are read-only copies of a blob at a point in time.
  • Versioning is enabled at Storage Account level → applies to all blobs.
  • Each version has a unique Version ID (timestamp string).
  • Deleting a blob when versioning is on does NOT delete previous versions.
  • To restore: copy a previous version → it becomes the new current version.
  • Soft Delete = protection against accidental delete, configurable 1–365 days.
  • Versioning + Soft Delete + Blob Snapshots can all be used together.
  • Cost: you pay for every version/snapshot stored (per GB).

Lab: Enable Blob Versioning & Test Restore
Duration: ~20 minutes · Azure Portal
1
Enable Blob Versioning

Go to Storage Account → Data management → Data protection → enable Enable versioning for blobs → Save.

2
Upload a File (Version 1)

Create a file notes.txt on laptop with text: "This is version 1" → upload to any container.

3
Update File (Version 2)

Edit notes.txt → change text to "This is version 2 — updated" → upload again (same filename). Azure saves version 1 automatically.

4
View All Versions

Click on notes.txt in the portal → click Version history tab → you will see both versions with their Version IDs and timestamps.

Expected Result
Two versions visible — current (v2) and previous (v1).
5
Restore Version 1

Click on the Version 1 entry → click Make current version (or download and re-upload). Now the file shows the original "version 1" text. Restore successful!

Key Learning
Even after overwriting a file multiple times, you can always restore any previous version using Blob Versioning.
6
Enable Soft Delete & Test

Data protection → enable Enable soft delete for blobs → set retention = 7 days → Save. Now delete notes.txt. Go back to container → click Show deleted blobs toggle → see the soft-deleted file → click Undelete → file is restored!
